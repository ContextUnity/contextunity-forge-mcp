# Forge MCP and CLI tool catalog

Use the active server registry and schemas as the final authority. This catalog is a compact navigation aid; repository-specific behavior and current schemas belong in that repository's reference docs.

## Task lifecycle

- `task_list(worktree?, repository?, milestone_ref?, milestone_status?, status?, stage?, detail?)` lists tasks; defaults to ready tasks in active milestones. `milestone` aliases `milestone_ref`; `parked` selects work waiting for a scope owner, and `cancelled` selects retained cancelled tasks.
- `task_claim(task_id, stage, worker_id, worktree, bundle?)` claims the current gate and returns its guidance/context. `task_submit(task_id, stage, action, evidence, findings?, worktree?)` submits claim-bound proof or review findings; its optional MCP routing selector does not change evidence identity.
- `task show TASK_ID` aliases `task inspect TASK_ID`. Inspect and submit accept `--task TASK_ID`; sync accepts `--file PATH`. Use `task list --detail compact|full`; `--full` is supported but cannot be combined with `--detail`.
- CLI-only milestone operations are `milestone init`, `list`, `show`, `handoff-context`, and `handoff`.
- `task_blackboard` posts, reads, or inspects `draft`, `notes`, `findings`, `blockers`, `decisions`, and `deferred` at milestone, task, or subtask scope. `gate` filters or targets posts/reads. `decisions` and `deferred` are copied with topic labels to delivery `architectural_notes`.
- Task results default to Markdown; request MCP `format: "json"` or CLI `--format json` when parsing values. Context Markdown retains profile guidance and task evidence; truncated blocker summaries include an inspect recovery.

## Discovery and search

All 20 MCP tools accept a `worktree` selector. It is optional except for `task_claim` and `task_manage(action="next")`, which require it for task affinity; this includes task, guide, and checkpoint tools. Without a selector, keep the canonical server root regardless of active claims. Use `worktree: "."` to select that root. An absolute path or a relative path containing a separator selects an existing directory directly; a missing explicit path returns `WORKTREE_NOT_FOUND`.

Relative path selectors are rooted at the server root.

Otherwise, search canonicalized and deduplicated Git-registered worktrees and immediate `.worktrees/` children in this order: exact directory name; literal prefix or pure-digit milestone prefix with leading zeroes removed; literal suffix; literal substring. The first nonempty tier must be unique. Multiple candidates return `WORKTREE_AMBIGUOUS` without falling through to a lower tier; no match or an empty selector returns `WORKTREE_NOT_FOUND`.

A selected worktree supplies its adapter/configuration, code index, milestone manifests, and checkpoints. Git-linked worktrees share the task database through existing task-store resolution; standalone repositories remain independent unless explicitly configured to share a store. MCP requests do not transmit the client's current directory. These human-friendly aliases are MCP-only: CLI queries choose a workspace with `--root`, and CLI task claim/next operations use an existing `--worktree` directory path.

On universal-routing servers, selection resolves a request-local root, adapter, and index before typed dispatch. Use `"."` for the server root or an existing absolute/server-relative directory path. Name lookup takes the first nonempty tier: exact name, literal or normalized numeric prefix, literal suffix, then literal substring. Multiple canonical candidates fail with `WORKTREE_AMBIGUOUS`; empty values, missing paths, and unmatched names fail with `WORKTREE_NOT_FOUND`. Omission retains the canonical server root, never an active claim's root. Git-linked worktrees still share the task database through existing `tasks_db` configuration. MCP requests do not transmit client cwd. CLI global `--root` (or its environment/current-directory default) selects a checkout; claim/next `--worktree` takes an existing affinity directory path, not the MCP alias cascade.

For efficient navigation, confirm workspace and coverage with overview, reuse sufficient search previews, inspect one declaration, and explain only when relation edges are needed. Fetch a snippet only when preview text is insufficient. Use full `get_doc` for the selected section; its default includes content. Exact `code_map_tests` call paths are verified test relationships; possible calls and lexical suggestions are not. Removal analysis is indexed static evidence, not runtime-safety proof. Lint reads stored syntax diagnostics; cycles are opt-in.

- `code_map_overview(aspects?, worktree?, limit?, offset?, detail?, generation?)` returns workspace root, components, counts, language coverage, profiles, and persisted primary/linked `coverage_by_workspace`. Database aspects are `counts`, `components`, `languages`, `coverage_by_workspace`, `cycles`, `compiled_profiles`, and `metadata`; adapter facets are `discovery`, `manifest_components`, `documentation_hubs`, and `milestones`. Omitted/empty aspects include all database aspects except opt-in `cycles`, plus adapter facets. Unknown aspects fail with the accepted set.
- `code_map_search(pattern, kind?, path?, exact?, include_docs?, include_preview?, group_by_file?, worktree?, detail?, limit?, offset?, generation?)` returns eligible exact name/qualname matches alone when present by default, otherwise ranked FTS/prefix results. `query` aliases `pattern`; `exact=true` requires an indexed exact name/qualname; `pattern="*"` needs a path or kind scope. Empty `path` is unfiltered. Results include signatures and `inspect_selector`; previews cover at most three hits, automatically for up to three total hits or on request for larger sets.
- `ast_grep_search(pattern, language?, path?, worktree?, detail?, limit?, offset?, generation?)` uses Tree-sitter `$NAME` and `$$$ARGS` captures. Omit `language` only with a recognized path extension; otherwise use a compiled profile ID from `code_map_overview`. CLI: `contextunity-forge-mcp ast grep --lang rust --path file.rs 'PATTERN'`; CLI `--lang` is required.
- `search_docs(query, doc_type?, component?, worktree?, limit?)` searches indexed docs, guides, and ADRs. `get_doc(path_or_id, section?, detail?, worktree?)` reads a Markdown document or exact heading anchor; it defaults to full section content, while `detail="compact"` returns an outline.

## Inspection and hierarchy

- `code_map_inspect(selector, worktree?, include_coverage?, show_doc?, show_source?, leading_lines?, max_body_lines?, source_offset?, generation?)` returns symbol summary, receiver metadata, exact callers/callees, verified `documented_in`, compact governing invariants, paged `analysis_gaps`, and candidate dispatch targets (`possible_calls`). Inspect Markdown shows one document page per citation; JSON retains its structured pages.
- `get_code_snippet(selector, worktree?, leading_lines?, max_body_lines?, source_offset?, generation?)` returns the complete digest-verified symbol when its serialized response fits the configured byte limit; otherwise it pages at complete source-line boundaries. It defaults to 5 leading lines plus the complete symbol and honors an explicit smaller body-line limit normalized to at least one. Every nonzero `source_offset` requires the previous page's explicit `generation`, even within one MCP session. Missing or stale tokens return a restart hint. An individually oversized line returns a budget error, not a partial line. Collection pagination also requires its generation.
- `code_map_explain(selector, direction?, worktree?, include_coverage?, show_doc?, show_source?, leading_lines?, max_body_lines?, source_offset?, generation?)` returns endpoint IDs, query-relative direction, ownership, invariants, and candidate dispatch; full detail includes stored edge evidence. Every nonzero source or collection offset requires the previous page's explicit generation. Inspect and explain retain configured 5-leading/200-body preview defaults and 1..500 body-line bounds. Explain retains its own `documents` page.
- `code_map_impact(selector?, changes?, direction?, depth?, worktree?, detail?, limit?, offset?, generation?)` traces inbound dependencies (default; exact `calls` and candidate `possible_calls`) or outbound dependencies, or accepts exactly one Git `changes` mode: `staged`, `unstaged`, or `head`. Depth-one non-seed nodes include selected edge endpoints, direction, location, and confidence. Change continuations bind graph and captured snapshot; inspect `unmapped_changes` and `complete`. A range maps only when its selected postimage matches the indexed file.
- `code_map_tests(selector, direction?, worktree?, detail?, limit?, offset?, generation?)` follows exact call paths from `test_case` roots or from tests into production. Helpers/fixtures may be path nodes, not roots. Bounded inbound lexical suggestions lack `call_path` and do not prove coverage.

## Verification and utility

- `code_map_prove_removal(selector, worktree?)` considers static references and blocks removal for candidate callers (`possible_calls`).
- `code_map_analyze(target, worktree?, lint?, include_cycles?)`: empty target means workspace diagnostics; a path means scoped diagnostics with digest-verified snippets/reasons where known. An unindexed non-empty path fails with `PATH_NOT_INDEXED`; indexed scopes with no diagnostics remain successful. `diagnostics` and `cycles` mode errors remain specific. Exact Markdown/MDX targets can include paged `doc_diagnostics` (`broken_doc_link`, `dead_doc_symbol`, `stale_doc_sections`); suggestions are not verified links. It also reports paged declared-public symbols unreachable from indexed test cases by exact calls. `lint=true` reads stored syntax diagnostics; `include_cycles=true` opts into cycles.
- `code_map_query(operation, selector?, worktree?, include_coverage?, depth?, limit?, offset?, generation?)` returns graph slices, unwired nodes, or read-only SQL with `operation="sql"`.
- `session_checkpoint(action, name?, content?, worktree?)` manages local JSON in the selected worktree's `.forge/checkpoints.json`; `forge_guide(topic?, force?, worktree?)` provides `acdd`, `query`, `adapter`, `docs`, or `ast` help.
- Selector forms include canonical node IDs; paths (`src/scanner.rs`, also stripping `file://`, `file:`, `./`); path+symbol (`src/scanner.rs:scan`); and path+line (`src/scanner.rs:42`, `src/scanner.rs#L42`, innermost node). Ambiguous bare names return candidates and never hijack to modules. `.md` selectors route to `get_doc` or `search_docs`.

## Documentation and invariant graph

Admitted Markdown/MDX, including milestones and plans, is indexed with section locations and frontmatter status. Confined relative links/wikilinks create `cites_doc`/`cited_by_doc` only when one section resolves. Documentary code claims are eligible in the source document's workspace unless an explicit normalized file path confines them elsewhere. Document, invariant, and component nodes do not verify claims. In each eligible claim occurrence, the first non-empty tier wins: exact normalized qualified name (`::` and `.` equivalent), exact declared name, then qualified-name segment suffix. Only one target in that tier creates a verified `referenced_symbols` relation; lower tiers are not combined.

Full `get_doc` pages ambiguous winning-tier `referenced_symbol_candidates`, each with source claim (`doc_id`, path, name, line) and target identity (`id`, name, qualname, kind, path, line). Candidates are navigation only: they create no `documents`, `references_doc`, `governs`, or `governed_by` edges and do not establish verified coverage. Compact detail omits candidate data and emits its full-detail hint once; MCP and CLI `docs get` default to full content. Inspect exposes verified `documented_in` once per cited section with `doc_id`, citation coordinate (`citation_line`), target declaration line, and resolved URI; explain retains its separate `documents` page. Impact exposes `affected_docs`, including a retained source-file claim after declaration deletion.

`INV-*` declarations become invariant nodes; only a verified unique symbol reference creates `governs`. Inspect, impact, and task context show at most five direct rules and five one-hop IDs with source locations and omitted counts. Suggestions, ambiguous candidates, and token similarity do not prove governance. This projection supplements, never replaces, task invariants, profile guidance, decisions, commands, or proof receipts.
